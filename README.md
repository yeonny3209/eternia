# 에테르니아 — 균열의 기록

> **Eternia: Chronicle of the Rift**
> 논타겟 액션 멀티플레이 오픈월드 RPG · 최고 레벨 50 · 무한 성장형 엔드 콘텐츠

기획서 `에테르니아_RPG_기획서_v2.md`를 따라 구현한 코드베이스입니다.
기획서 16부 로드맵이 지시한 순서 — **데이터보다 시스템을 먼저** — 를 그대로 따라
**M0(기반) 전량 + M1(액션 전투 코어) + M2(장비 엔진·도구)** 를 실제 동작하는 코드로 만들었습니다.

**▶ 지금 바로 플레이**: <https://yeonny3209.github.io/eternia/>
닉네임을 정하고 여명 마을에서 시작합니다. 설치도 로그인도 필요 없고, 진행은 브라우저에 저장됩니다.

## 아직 안 되는 것

- **멀티플레이(M4)** — Colyseus Room이 없습니다. 전투 코어는 서버 권위 형태로 짜여 있어 그대로 얹으면 됩니다.
- **PostgreSQL 연결** — Prisma 스키마는 완성돼 있으나 현재 저장소는 인메모리입니다.
- **튜토리얼 T-01~T-11** — 캐릭터 생성 후 바로 오픈월드로 들어갑니다. 연출된 튜토리얼 구간은 없습니다.
- **던전·레이드 인스턴스** — 데이터(30종/25종)는 있으나 진입 가능한 방은 없습니다.
- **퀘스트 데이터 161종** — 맵 1~3 + 일일/주간/월드까지 50종만 투입했습니다(M5 범위). 나머지 맵에는 NPC는 있지만 의뢰가 없습니다.

## 구조

```
eternia/
├── packages/
│   ├── shared/          # ★ 판정 로직 전부. 클라·서버가 같은 코드를 쓴다
│   │   ├── combat/      #   히트박스, 상태 머신, 스태미나, 자세, 가드
│   │   ├── formulas/    #   데미지 공식, 성장 곡선, 어그로
│   │   ├── items/       #   접사 롤, 강화/재련/각인
│   │   ├── quest/       #   퀘스트 엔진
│   │   ├── validators/  #   닉네임
│   │   └── data/        #   모든 기획 데이터(JSON)
│   ├── server/          # Express + JWT, Prisma 스키마
│   └── client/
│       ├── world/       #   맵 생성, 월드 씬, 플레이어 상태·저장
│       ├── ui/          #   HUD, 인벤토리, 퀘스트, 월드 지도, 대화
│       └── scenes/      #   훈련장(프레임 튜닝용)
└── tools/
    ├── validate-data.ts
    ├── generate-items.ts
    └── balance-sim.ts
```

**설계의 핵심은 `packages/shared`입니다.** 기획서 2-2의 "모든 판정은 서버가 한다"를
지키려면 판정 코드가 한 벌이어야 합니다. 클라이언트는 같은 코드를 예측 재생에만 씁니다.
훈련장 데모가 서버 없이 도는 것도 이 때문입니다 — 화면에 보이는 판정은
서버가 돌릴 코드와 **문자 그대로 같은 코드**입니다.

## 기획서 대비 주요 구현 노트

### 무적 프레임은 서버 타임스탬프로만 판정한다

기획서 6-3-6이 못 박은 부분입니다. 클라이언트의 "나 지금 무적이었어"는 믿지 않습니다.
`StaminaController`가 회피 수신 시각에 `[t, t+300ms]` 구간을 **기록해 두고**,
히트 판정 시각을 인자로 받아 답합니다.

```ts
stamina.dodge(1000);                    // 서버 수신 시각
stamina.wasInvulnerableAt(1150);        // true  — 되감기 판정에 그대로 쓴다
stamina.wasInvulnerableAt(1400);        // false
```

과거 시각을 물어볼 수 있으므로 M4의 지연 보상(최대 200ms 되감기)에 그대로 얹힙니다.

### 한 틱에 여러 페이즈를 통과해도 판정을 건너뛰지 않는다

서버 틱이 33ms인데 프레임 합이 그보다 짧은 스킬이 있습니다.
상태 머신이 단순히 `if`로 페이즈를 넘기면 그런 스킬은 **판정이 통째로 사라집니다.**
`ActionStateMachine.update()`가 while로 도는 이유입니다.

### 히든은 코드 레벨에서 감춘다

기획서 8부·9-3절이 요구한 것을 규칙이 아니라 구조로 지켰습니다.

- `QuestTracker.visibleLog`가 히든 퀘스트를 걸러냅니다
- `/api/data/*`가 히든 맵·히든 퀘스트·해금 조건을 내려주지 않습니다
- `validate-data.ts`가 `autoTrack: true`인 히든 퀘스트를 **오류로 잡습니다**
- 서버 테스트가 응답 JSON에 `unlockSteps`가 없는지 확인합니다

### 몬스터 HP는 손으로 정하지 않았다

기획서 6-3-5의 "동레벨 일반 몬스터는 3~5타에 사망"이 검증 가능한 값이 되려면
플레이어 공격력이 정의돼 있어야 합니다. `referencePlayerAtk(level)`을 기준선으로 두고
거기서 HP를 역산했고, **테스트가 monsters.json 전체를 그 기준으로 검사합니다.**
기준선을 바꾸면 테스트가 먼저 깨집니다.

## 기획서와 다르게 한 것

정직하게 적어 둡니다.

| 항목 | 기획서 | 실제 | 이유 |
|---|---|---|---|
| 클라이언트 렌더러 | PixiJS | Canvas 2D | M1에서 검증할 것은 렌더러가 아니라 히트박스 판정입니다. 렌더 레이어는 `TrainingScene.render()` 하나로 격리해 두었으니 교체 비용이 낮습니다 |
| 패키지 매니저 | pnpm | npm workspaces | 환경에 pnpm이 없었습니다. 워크스페이스 구조는 동일합니다 |
| DB | PostgreSQL | 인메모리 (스키마는 Prisma로 작성) | DB 없이도 서버가 뜨고 테스트가 돌아야 해서입니다. `Repository` 인터페이스만 구현하면 라우트는 그대로입니다 |
| 접사 종수 | 접두 8계열 × 6티어 = 48 | 계열당 정의 1개 × 6티어 | 기획서의 산술(48)에 정확히 맞췄습니다. 계열 안에서 변형을 늘리려면 정의를 추가하면 됩니다 |

## 밸런스 시뮬레이터가 지금 찾아낸 것

기획서 6-4-9이 "건너뛰지 말라"고 한 도구입니다. 현재 출력:

- **접사 조합** — 상위 0.1% / 중앙값 = **약 1.6배**. 기준(3배) 이내입니다.
- **직업 DPS 편차** — 목표(±7%)를 크게 벗어나 있습니다. 계수는 기획서 값을 그대로 넣은
  1차 입력이고, 기획서도 "수치는 M1~M2 플레이테스트로 조정"이라고 명시했습니다.
- **히든 직업 성능 상한** — 일부가 105%를 넘습니다. 기획서 8부는 히든이
  기존 직업보다 강하면 안 된다고 못 박았으므로, **히든 스킬 라인의 계수를 낮추거나
  기본 스킬 일부를 대체하는 형태로 바꿔야 합니다.** 이것이 현재 최우선 튜닝 과제입니다.

이 도구는 게이트가 아니라 관측기입니다. CI를 막지 않고 수치만 보여줍니다.
